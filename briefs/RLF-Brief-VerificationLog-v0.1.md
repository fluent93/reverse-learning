## 1. Purpose

This brief defines the scope, purpose, and design requirements for the next Reverse Learning Framework output:

**RLF-Log-Verification-v1.0**  
**Reverse Learning Verification Log: Documenting Evidence Behind AI-Assisted Work**

The Verification Log will extend **Part 3: Verification** of the RLF Checklist v1.0 into a focused, repeatable, evidence-based recording tool.

The purpose of the log is to help learners document:

- what they questioned in an AI-generated output,
- what evidence they used to verify it,
- what decision they made,
- what they changed in the final artifact,
- and what they learned through the verification process.

---

## 2. Positioning Statement

The Verification Log is not a replacement for the full Reverse Learning Checklist.

It is an execution and evidence tool for **Part 3: Verification**.

> The Reverse Learning Verification Log helps learners turn verification from a private mental act into a visible evidence trail. It documents how AI-generated claims or elements were questioned, checked, revised, removed, or retained.

---

## 3. Core Principle

**Verification is not just fact-checking. It is a learning activity.**

In Reverse Learning, verification is not a final compliance step. It is a core mechanism through which learners move from passive acceptance of AI-generated output to explainable ownership.

A learner does not demonstrate understanding merely by saying, “I checked it.” The learner demonstrates understanding by showing:

- what was checked,
- why it needed checking,
- what source or evidence was used,
- what conclusion was reached,
- what changed as a result,
- and what was learned.

---

## 4. Relationship to RLF Checklist v1.0

The RLF Checklist v1.0 provides a full seven-stage process:

1. AI-Generated Artifact
2. Learner Skepticism
3. Verification
4. Iterative Prompting
5. Contextual Integration
6. Human Reconstruction
7. Explainable Ownership

The Verification Log focuses only on Stage 3.

| RLF Checklist v1.0 | RLF Verification Log |
|---|---|
| Full seven-stage process | Focused tool for Part 3: Verification |
| Helps learners review the whole AI-assisted learning process | Helps learners document verification evidence in detail |
| Includes a mini-log for verification | Expands the mini-log into a repeatable evidence trail |
| Suitable for reflection and process review | Suitable for submission, review, coaching, or audit |
| Broad and comprehensive | Narrow and operational |

## 5. Primary User and Secondary Reader

### Primary User

The primary user is the learner or knowledge worker who used generative AI to create, revise, summarize, analyze, or improve an artifact.

Examples:

- student writing a paper with AI assistance
- employee preparing an AI-assisted report
- instructional designer drafting a lesson plan
- researcher reviewing an AI-generated literature summary
- developer checking AI-generated code or documentation
- manager reviewing an AI-assisted business proposal

### Secondary Reader

The secondary reader is the person who needs to evaluate the quality of the learner’s verification process.

Examples:

- instructor
- facilitator
- manager
- reviewer
- coach
- peer reviewer
- AI literacy trainer

## 8. Design Requirements

The Verification Log should be:

### 1. Focused

It should only address the verification stage, not the entire Reverse Learning process.

### 2. Evidence-based

It should require visible evidence, not only self-reported claims.

### 3. Lightweight enough to use

It should be practical for real assignments, reports, or workplace artifacts.

### 4. Strong enough to prevent performative compliance

It should discourage shallow entries such as “I asked ChatGPT again” or “It sounded correct.”

### 5. Learner-facing but reviewer-readable

A learner should be able to complete it, and a reviewer should be able to assess whether meaningful verification occurred.

### 6. Compatible with multiple contexts

It should be usable in academic, corporate learning, instructional design, and professional knowledge work settings.

## 9. Main Log Template: Required Fields

The core log should include the following fields:

| Field | Purpose |
|---|---|
| AI-Generated Claim or Element | Identifies the claim, paragraph, data point, source, code, design choice, or recommendation being checked |
| Why I Questioned It | Explains why the learner did not accept it immediately |
| Verification Method | Describes how the learner checked it |
| Source / Evidence Used | Documents the source, reference, standard, test, or material used |
| Evidence Quality | Rates or describes the credibility of the evidence |
| Verification Result | Records whether the element was accurate, partially accurate, unsupported, incorrect, or uncertain |
| Decision | Indicates whether the element was kept, revised, removed, or marked for further review |
| Revision Made | Shows what changed in the final artifact |
| What I Learned | Captures the learning that occurred through verification |

The most important field is:

**What I Learned**

Without this field, the log risks becoming a simple fact-checking form. With this field, the log becomes a Reverse Learning tool.

---

## 10. Recommended Verification Results

| Result | Meaning |
|---|---|
| Accurate | The claim or element was supported by credible evidence |
| Partially Accurate | The claim had some support but required qualification or revision |
| Unsupported | No credible evidence was found |
| Incorrect | The claim contradicted credible evidence |
| Uncertain | The evidence was inconclusive or insufficient |

---

## 11. Recommended Decision Categories

| Decision | Meaning |
|---|---|
| Keep | Retain the element as originally generated |
| Revise | Modify the element based on verification |
| Remove | Delete the element because it is unsupported, incorrect, or irrelevant |
| Qualify | Add limitation, condition, or uncertainty |
| Further Review | Mark for later checking or expert review |

---

## 12. Evidence Quality Guide

The log should include guidance on evidence quality.

| Evidence Type | Stronger Use | Weaker Use |
|---|---|---|
| Peer-reviewed source | Used to verify conceptual or empirical claims | Cited without understanding or relevance |
| Course material | Used to align with assignment expectations | Mentioned without checking the actual content |
| Official documentation | Used for technical, legal, policy, or procedural claims | Used without checking date, version, or scope |
| Expert source | Used with context and limitations | Treated as unquestionable authority |
| Dataset or calculation | Used to test a numerical or empirical claim | Accepted without checking assumptions |
| Code execution or test | Used to verify whether generated code works | Assumed correct because it looks plausible |
| AI follow-up response | Used to generate questions or possible checks | Treated as sufficient verification by itself |

Important rule:

> AI follow-up responses can support verification, but they are not sufficient evidence by themselves.

---

## 13. Weak vs. Strong Verification Examples

| Weak Verification | Strong Verification |
|---|---|
| “I asked ChatGPT if this was correct.” | “I checked the claim against an official source and revised the statement.” |
| “The citation looked real.” | “I opened the source and confirmed that it supports the claim.” |
| “The answer sounded reasonable.” | “I compared the answer with course materials and identified one missing condition.” |
| “I edited the wording.” | “I changed the claim because the evidence only partially supported it.” |
| “I found a website that agreed.” | “I compared two credible sources and noted where the AI output oversimplified the issue.” |

---

## 14. Recommended Use Levels

| Use Level | Estimated Time | Best For |
|---|---:|---|
| Quick Verification | 10–15 minutes | Low-stakes drafts, short reflections, informal summaries |
| Standard Verification | 25–40 minutes | Assignments, reports, lesson plans, workplace documents |
| Deep Verification | 60+ minutes | Academic writing, high-stakes decisions, professional deliverables |

## 19. Korean Summary

**RLF Verification Log**는 Reverse Learning Checklist v1.0의 Part 3: Verification을 실행·제출·평가 가능한 증거로 남기기 위한 도구다.

이 도구의 목적은 학습자가 단순히 “검토했다”고 말하는 것이 아니라, 실제로 다음을 기록하게 하는 것이다.

- AI 산출물 중 무엇을 의심했는가
- 왜 그 부분을 검증해야 한다고 보았는가
- 어떤 근거를 사용했는가
- 검증 결과는 무엇이었는가
- 유지, 수정, 삭제, 보류 중 어떤 결정을 했는가
- 최종 산출물에서 무엇을 바꾸었는가
- 그 검증 과정을 통해 무엇을 배웠는가

핵심 원칙은 다음과 같다.

**검증은 단순한 사실 확인이 아니라 학습 활동이다.**

따라서 Verification Log는 단순한 fact-checking 양식이 아니라, AI 산출물을 설명 가능한 자기 지식으로 바꾸기 위한 Reverse Learning 도구다.
